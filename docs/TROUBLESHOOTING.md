# 故障排查与移除

所有命令在项目根目录执行。常规启动使用普通用户运行 `./vpn-new`；管理员密码仅在终端的 sudo 提示中输入，VPN 账号和验证码在客户端中输入。

## 启动后退出，或残留 PromoteService

最早的修订 1 等待 RPC 服务的时间不足，UI 会在服务刚开始监听前退出。修订 2 已增加重试到 15 次，并防止回退扫描其他实例端口。

正常退出目标副本后，可修复与记录精确匹配的旧版副本：

```sh
sudo python3 univpn_multi.py repair --number 2
python3 univpn_multi.py start --number 2
```

修复先校验源文件、旧副本及补丁内容，备份后只更新 UI 中的重试指令和完整性记录；不修改原版。界面或连接后台仍在运行时拒绝修复。确认仅有本副本孤立提权服务时，才尝试 SIGTERM，不强制停止隧道。

若脚本拒绝确认进程路径、文件哈希或权限，请先查看具体提示。不要直接放宽安装目录权限或结束全部同名 VPN 进程。

## 系统配置文件读取会话失败

受支持客户端安装模板的重连时间为 0，但后台仅接受 1–1440。读取错误会触发重建用户配置并清空 Session 索引，导致 GUI 无法显示已存在的网关。当前新构建和 `vpn-new` 已处理该问题。

对于旧副本，先正常断开并彻底退出它，再执行：

```sh
sudo python3 univpn_multi.py repair-config --number 2
python3 univpn_multi.py start --number 2
```

命令备份该副本的安装系统配置、用户系统配置及 key.ini，再修复无效重连时间、缺失会话索引和厂商模板校验记录。已有会话设置及网关文件保留；恢复的空白会话不会自动保存密码或登录。备份在 `~/.UVP002/.multi-backups/paired-config-*`。

仅删除并重新导入同名网关、只补 Session 或只修改所有者，不能解决重连时间无效造成的重建。实现依据见[配置重建分析](ANALYSIS.md#配置重建问题)。

## 导入提示配置已经存在，但列表为空

可能是该副本 `~/.UVPnnn/config/` 内网关文件尚在，但 sysconfig.ini 的 Session 索引已丢失。先按上一节修复；不需要直接删除文件或备份，也不要清理原版 `~/.UniVPN`。

需要同步原版最新同名配置时，对下一个将启动的空闲副本使用：

```sh
./vpn-new --sync-original
```

## 第二条连接后第一条掉线，或第三条无法建立连接

已复现的原因是全隧道接管默认出口；第一次修复仅保护两个网关，第三个网关未被保护。当前默认扫描**全部原版已保存网关**，没有将并发数量限制为两条。

```sh
python3 gateway_routes.py inspect
sudo python3 gateway_routes.py protect
```

`protect` 保留现有正确保护，只补缺少的 `/31`。已有连接稳定时无需断开它们，补齐保护后只重试未连接的网关；已因错误出口掉线的连接需正常断开再重新登录。验证码在各自窗口输入。

每条 `/31` 除网关外还覆盖一个相邻公网 IP。路由保护不改默认路由、业务网段或 DNS；只能处理原版 config 中保存的公网 IPv4 地址。域名、IPv6、私网网关及仅存在于副本中的配置需要另行分析。

如果报物理出口不唯一，先确认当前物理接口，再给命令加 `--interface en0`。若首次保护前全隧道已移除物理默认路由，且没有可验证的既有保护，脚本会拒绝猜测出口；应正常断开相关 VPN，确认普通网络恢复后重新检查和应用。

换 Wi-Fi 或有线网络后，不应沿用旧下一跳。正常断开相关 VPN，检查并撤销旧保护，再在新网络重新应用：

```sh
sudo python3 gateway_routes.py restore
python3 gateway_routes.py inspect
sudo python3 gateway_routes.py protect
```

没有长期后台监控；系统重启后同样需要检查。若恢复记录中的条目已被其他程序改过，撤销会停止，应先检查实际路由，避免直接全局清空。

## 登录认证失败

副本不修改认证结果、短信逻辑或证书校验。观测到的通用认证失败码 `0x30001` 无法单独区分密码错误和服务器账号策略，日志中的 `mac addr auth` 标签也不能证明 MAC 绑定。

先确认同一网关在原版中可用，并检查连接是否已经进入账号认证阶段。网关初始 SSL 超时与账号认证失败应分别排查；必要时由网关管理员查询服务端拒绝原因。不要在问题反馈中附带密码、短信验证码或认证报文。

## 在线但业务或域名无法访问

网关出口保护仅维持 VPN 的公网连接。请依照[业务验收步骤](VALIDATION.md#业务验收步骤)，分别检查目标 IP 的实际路由、DNS 和业务。多个实例仍共享系统 DNS、代理和路由；相同业务 IP、网关强制策略等无法仅靠改进程名称解决。

## 正常退出与移除

1. 在目标窗口中正常断开 VPN，并从菜单栏彻底退出该副本。
2. 确认该副本的界面、提权服务和连接后台均已退出。
3. 仅移除对应 `/Applications/UVPnnn.app`。需要清空副本数据时，再单独移除对应的 `~/.UVPnnn`，其中可能含保存的登录记录和备份。
4. 不再需要多实例网关保护时，在相关 VPN 正常断开后执行 `sudo python3 gateway_routes.py restore`。

不要使用厂商卸载程序移除副本，也不要删除 `/Applications/UniVPN.app` 或 `~/.UniVPN`。不要用 `kill -9` 代替正常断开，否则可能遗留厂商路由、DNS 或代理设置。工具没有自动回滚厂商客户端全部网络修改的能力。
