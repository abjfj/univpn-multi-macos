# macOS 构建与实现分析

分析日期：2026-10-20。本文记录受支持样本的技术依据；运行结果统一见[验证说明](VALIDATION.md)。不包含厂商二进制、真实网关配置、账号或日志。

## 兼容性门槛

源 App 固定安装于 `/Applications/UniVPN.app`。`Info.plist` 的版本为 `10781.19.0.1214`，原 Bundle ID 为 `work.VPNClient`。以下相对路径均以 `Contents/MacOS` 为根：

| 文件 | SHA256 |
|---|---|
| `UniVPN` | `c0fed6a4bf6d150df6413263283984bf4c9ef51e371da37fd45f033e8ad28408` |
| `promote/UniVPNPromoteService` | `d36a2e951c52e344a414b449b41f017248d127f1234ac1e83f9b80a290a53c9e` |
| `serviceclient/UniVPNCS` | `426a59bb1342ec5cff995581c9b3d1fbba622b7bcc623dc468a16c9b5b4f19f1` |

三个文件均为 x86_64 Mach-O，样本未签名。只匹配版本号不足以安全应用固定偏移补丁，必须通过完整 SHA256、原始指令字节和身份字符串数量检查。不支持 Universal binary、原生 arm64 或其他哈希。

## 实例身份与端口

对副本等长替换 `UniVPN` → `UVPnnn`，不改文件长度、节偏移和函数布局。UI 30 处、Promote 8 处、Backend 7 处；Backend 另有两处小写 `univpn` PAC 文件名。同步改名资源、固定安装路径、Bundle ID、进程、用户配置目录、日志目录及流量 socket。

| 项目 | 原版 | 实例 2 | 实例 3 |
|---|---|---|---|
| App | `UniVPN.app` | `UVP002.app` | `UVP003.app` |
| UI / 单实例键 | `UniVPN` | `UVP002` | `UVP003` |
| 提权服务 | `UniVPNPromoteService` | `UVP002PromoteService` | `UVP003PromoteService` |
| 连接后台 | `UniVPNCS` | `UVP002CS` | `UVP003CS` |
| 配置及日志目录 | `~/.UniVPN` | `~/.UVP002` | `~/.UVP003` |
| RPC 端口 | 29191 | 31006 | 31009 |
| 插件初始端口 | 29192 | 31007 | 31010 |
| 后台初始端口 | 19060 | 31008 | 31011 |
| Unix socket | `/tmp/UniVPNFlow` | `/tmp/UVP002Flow` | `/tmp/UVP003Flow` |

实例 N 的端口块为 `31000 + 3*N`，RPC、插件、后台依次取块内 0、1、2。编号范围 2–999 的块互不重叠，但厂商代码在绑定失败时可能尝试后续端口，仍需检查实际监听。

Qt `SingleApplication` 从可执行文件 basename 建立 `QLocalServer`，因此仅更改 App 名称不足以解除单实例限制，还需要改可执行文件名。副本内部的后台重启命令也同步改名，避免命中原版进程。副本移除未适配的升级程序和升级助手，防止升级恢复原版身份。

## 补丁偏移

以下均为**文件偏移**，该样本的 `__TEXT` 基址为 `0x100000000`。修订版本为 2：

| 文件 | 偏移 | 行为 |
|---|---|---|
| UI | `0xE6149`–`0xE6163` | 从 applicationFilePath 取文件名作为单实例键；保留逻辑，仅改文件名 |
| UI | `0xF5DC8` | RPC 端口初始化：原 `c7 45 b4 07 72 00 00` |
| UI | `0xF5E79` | RPC connect：原 `bf 07 72 00 00` |
| UI | `0xF5E6F` | `83 7d b0 02` → `83 7d b0 0f`，默认 RPC 尝试从 2 次增至 15 次 |
| UI | `0xF5EF4` | 将回退扫描上限设为本实例 RPC 端口，避免扫描原版端口 |
| UI | `0xF7F4C` | 插件初始端口：原 `bf 08 72 00 00` |
| Promote | `0x57C6` | RPC listen：原 `bf 07 72 00 00` |
| Backend | `0x11853` | 后台初始端口：原 `c7 45 c0 74 4a 00 00` |
| UI | `0xF3520` | 权限校验 `04777` → `04755`，保留 root:wheel 要求 |
| UI | `0x206E90` / `0x206EA9` | 授权命令中的后台 `04777` → `04755`、目录 `04777` → `00755` |
| Backend | `0x394172`–`0x3941D1` | utun 编号尝试循环，未修改 |
| Backend | `0x394005`–`0x394043` | 编号 + 1 作为控制接口 unit，未修改 |
| Backend | `0x394205`–`0x394219` | getsockopt 获取实际接口名，未修改 |
| UI | `0xF8260` 起 | 取最大编号、已启用 utun 的 IPv4，未修改，显示归属可能不准确 |

冷启动修订依据：原 UI 在 t=0、t=1 秒尝试连接，而观测到提权服务约在 t=1.114 秒才监听，导致 UI 退出并留下服务。扩大指定端口的等待时间后，副本三类进程已实际正常启动。没有屏蔽 RPC 失败判断。

## 文件与进程防护

- `build` 只写输出副本；校验源文件和内部链接，拒绝越界或失效链接、特殊文件及已有输出目录。不在生成目录设置 setuid，UI 暂设为 `0644`。
- Manifest 记录完整载荷、链接目标、二进制哈希、端口和身份。它用于检测意外改动，并非开发者签名或供应链真实性证明。
- `install` 使用 root 私有临时目录校验复制结果，设置 root:wheel 和不可组写/其他用户写的权限，后台为 `04755`，完成后发布到 `/Applications`；拒绝覆盖既有 App。
- 已安装 App 的 `Contents/MacOS/sysconfig.ini` 是厂商可变运行数据，允许内容变化，仍检查普通文件、root:wheel 和写权限。其余文件继续完整性校验。
- 通过 `proc_pidpath` 确认同名进程的实际路径，UI 或后台运行时拒绝重用和配置写入。无 UI、无后台时，仅确认属于本副本的孤立提权服务可用 SIGTERM 清理。
- `new` 用文件锁避免同一项目并发选中同一实例；`--dry-run` 不创建、安装、启动或修改网络。

## 配置重建问题

安装模板的 `ADVANCED/ClientReConnectTimeValue=0` 与后台读取器要求不一致：

1. Backend `0x71D0`–`0x7218` 要求数值在 1–1440，缺省为 5；0 返回读取错误。
2. `0x86D5` 累加错误，`0x8738` 未进入成功分支。
3. 经 `0x8745` 删除用户配置、`0x87E2` 重建默认配置，全部 `SessionN` 索引丢失。

网关文件仍存在，因而 GUI 不显示会话，但再次导入会提示同名文件存在。只改文件所有者、只补 Session，或只同步两份配置及校验值，都无法消除无效字段触发的重建。

当前构建和修复将无效整数恢复为 5，保留有效值；格式异常则拒绝处理。根据现存网关文件恢复缺失 Session 索引，不覆盖既有会话，不为恢复的空白会话启用保存密码或自动登录。

厂商 `key.ini` 的 `GLOBAL/VerifyValue` 是安装模板的 SHA256（相关函数 `0xBC30` / `0xB900`），不是不断变化的用户配置的哈希。首次准备副本时仅在缺少 key.ini 的情况下初始化；已有 key 不变。`repair-config` 备份后同步该副本的安装配置、用户配置和校验记录，不屏蔽校验分支。

本机修正后触发配置重读、正常退出并重启，重连时间和 Session 均保留，点击连接进入登录窗口，随后用户已成功登录。

## 已保存登录记录继承

在同一 Mac 上，将原版网关文件及 Session 的 `ConnectType`、`RemPwd`、`AuthType`、`LastLoginAddr`、`ProfileName`、`ProfileUser`、`ProfileInfo` 等字段合并到空闲副本。`ProfileInfo` 保持厂商保存格式，不进行解密；不复制原版 GLOBAL/ADVANCED 身份和 key.ini，所有继承会话的 AutoLogin 为 0。

源配置读取两次确认快照一致，写入前再次检查副本未运行。默认保留同名配置；`--sync-original` 备份后覆盖。备份目录 `0700`、新配置 `0600`；写入失败回滚本次已写文件。该功能不保证跨机器或跨构建的保存记录兼容性。

## 网关路由保护

实测全隧道接管默认路由后，另一实例的监控循环暂时删除自身 `/32` 网关路由，随后错误选择其他 utun，导致重连失败。最初只保护两条网关时，第三条未保护的网关也在初始 SSL 阶段超时；扩展至全部已保存网关后，用户验证三条保持在线。

`gateway_routes.py` 为每个已保存公网 IPv4 网关计算 `/31`，通过物理下一跳添加独立回退路由。`/31` 比 `/32` 宽但比默认路由具体，在厂商暂时删除 `/32` 时继续生效，同时额外覆盖一个相邻公网 IP。相同 `/31` 去重，已有匹配出口保持，已有冲突出口拒绝覆盖。

物理出口优先查询 en 接口的 scoped default；若全隧道已删除物理默认路由，则从已有 PROTO2 保护条目恢复候选，并检查下一跳在该网卡直接可达。不能唯一验证时拒绝猜测。

新增路由使用 `-static -proto2`，状态以 root:0600 保存在 `/var/run/univpn-multi-gateway-routes.json`。全局锁避免并发；添加失败只回滚本次新增，无法安全回滚时保留恢复记录。撤销前校验已记录条目的前缀、下一跳、接口及 PROTO2 标记，拒绝删除被其他程序改变的路由。具体命令语法依据目标机器随附的 `route(8)`。

这些修改不隔离系统路由、DNS 或代理，也不保证所有业务网段并存；没有修改 utun 分配、认证结果或证书校验。
